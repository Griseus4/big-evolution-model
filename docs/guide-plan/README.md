# Серия полного описания проекта: инструкция исполнителю

Статус: пользователь разрешил всю серию P00–P28 без согласования каждой главы. Завершены пакеты A–D (P00–P19); остальные выполняются последовательно. Охват — в [реестре](coverage.md).

## Результат и границы

Цель серии — во вкладке «О проекте» объяснить всю действующую модель и работу приложения: от питания и решений жителя до экспериментов, статистики, файлов и разработки. Читатель должен найти ответ через дерево/поиск, понять причинную связь и при необходимости перейти к реализации. Переписывать каждую строку кода словами не требуется.

База планирования — 0.54.8; перед выполнением сверить реальную версию и изменения после неё. Часть глав уже содержательно проверена: вводная, время, география, действия, энергетика, каталог чисел. Их не писать заново; проверить только затронутые связи и найденные пробелы. Остальные статьи и наличие ссылок на файлы не означают полного описания.

Разрешение выполнить эту серию включает статьи, выжимки, поиск, оглавление, паспорта, числовые привязки, простые поясняющие схемы, проверки справочника и сопроводительные документы. Оно не включает изменение физики, обучения, RNG, наследования, статистических методов, форматов сохранений или новую систему питания. Для числовых примеров использовать существующий расчёт; если его нельзя безопасно вызвать из справки, дать символический пример либо зафиксировать отдельную задачу, не переносить расчёт модели ради статьи. Отдельная интерактивная карта всех глав остаётся отложенной.

Принятые требования к будущей работе уточнять в соответствующем тематическом стандарте без дублирования и разрастания AGENTS.md.

Не выдумывать объяснение, чтобы закрыть этап.

## Как запускать и продолжать

Пользователь может поручить один пакет, несколько пакетов или всю серию. После завершения патча переходить к следующему разрешённому без промежуточной команды. Завершение пакета не разрешает пакет, который не был поручен. Параллельные агенты для этой серии не требуются.

В начале рабочего сеанса: AGENTS → START_HERE → work/current → этот маршрут → только карточка текущего патча. Прочитать стандарт статьи и числовой контракт один раз за сеанс. Затем искать конкретные символы через `rg`; читать функции и непосредственных потребителей. Не загружать заранее все исходники, архив, тестовые логи и главы.

Восстановление после потери контекста: сначала контрольная запись, затем строка этапа в его пакете и изменённые файлы. Зафиксированное завершение не повторять; незаконченные проверки не считать выполненными. Контрольная запись хранит разрешённый диапазон, текущий ID, результат, проблему и следующий конкретный шаг. Реестр охвата хранит доказательства по темам, а протокол выпуска — историю результата.

## Один патч: обязательный рабочий цикл

1. **Объём.** Прочитать карточку, существующую статью и её sources/related. Найти рабочий путь вызовов: наличие функции в старом модуле не означает её использования текущим миром. Источники карточек — точки входа, не исчерпывающий список доказательств.
2. **Карта фактов.** Для существенных утверждений записать в реестр охвата: вопрос → статья/раздел → файл/символ → существенная граница или исключение → способ проверки. Проследить владельца состояния, вход, преобразование и наблюдаемый результат. Несовпадение текста, кода и принятого контракта оставить явным.
3. **Текст.** Написать простое объяснение, пример, раскрываемые точные правила, связи и источники по стандарту статьи. Избегать цепочек через запятую, банальных оговорок и повторения одной мысли. Пошаговый процесс — нумерация; сравнение — небольшая таблица. Схему использовать для причинной связи. Длинный текст хранить один раз в тематическом `guide-*-text.js`.
4. **Числа.** Значения правил брать из именованных экспортов; принятые настройки — через `guide-parameters.js` с явным контекстом. Не выдавать базовое значение за настройки загруженного мира. Пропуск не заменять нулём. Пояснение формулы и условие её применения проверять отдельно от числовой подстановки. В справке не запускать симуляцию и не добавлять работу на каждый подшаг.
5. **Подключение.** Сохранить устойчивые ID и старые ссылки. Новую статью внести в дерево, текстовый каталог, реестр, поисковые термины, выжимку и паспорт; related должны вести к настоящим статьям. Новые дочерние статьи допустимы. Старые вводные статьи использовать как вход, не дублировать в них подробности. Указатели реестра — по символам, без ручных номеров строк.
6. **Самопроверка смысла.** Снова открыть источник для каждого существенного вывода, особенно отрицания, порядка фаз, границы и знаменателя. Проверить пример в обычном и граничном случае. Исправить прозу, если она утверждает больше, чем код. reviewedVersion ставить только содержательно сверенным статьям.
7. **Проверки.** Выполнить подходящие проверки согласно разделу ниже, записать точные команды/результаты. Проверка наличия слов не доказывает механику. Не подгонять тестовые ожидания под удобный текст.
8. **Закрытие.** Обновить строку этапа, реестр охвата, затронутую карту/контракт, протокол и контрольную запись. Для изменения пособия приложения оформить обычный выпуск; для одних правил работы версия игры не нужна. Производные материалы — только экспортёром. Публиковать по постоянному маршруту проекта, не добавляя проверки только ради push. Затем продолжать разрешённый диапазон.

## Что проверять

Обязательный минимум документов: `python tools/verify-local.py --only docs`. Если появились модули/DOM/привязки справки, добавить существующую проверку wiring/синтаксиса по [локальному циклу](../workflows/local.md) и соответствующие тесты пособия. Карточки указывают тесты для чтения и выбора: запускать затронутые сценарии, не весь перечень автоматически на каждой статье.

Новую исполняемую проверку писать для нового расчётного примера, контекстного значения, навигационного контракта или действительно незащищённого поведения. Для простой правки прозы достаточно сверки источников и документов. Не писать тест, который лишь ищет предложение и тем самым объявляет его истинным. Старые ожидаемые результаты сохраняют независимость от проверяемой формулы.

При изменении видимой структуры справочника проверить его в браузере в рамках реализации, если браузер доступен: дерево, поиск, ссылка/возврат, выжимка по наведению и фокусу, раскрытие правил, длинная таблица, узкое окно. Это не дополнительная проверка ради публикации. Если выполнен только поддельный DOM, так и написать; визуальную проверку не объявлять пройденной. Не делать скриншоты всех неизменённых глав при каждом патче.

Известные прежние сбои искать в [проверках](../verification.md), не считать перечень неизменным. В частности, старый тест импорта полного мира 0.45.0 не разрешает расширять совместимость ради зелёного отчёта. Новую ошибку локализовать; блокирующий дефект справочника исправить, спор модели оставить отдельным вопросом.

## Реестр охвата и критерий полноты

P00 создаёт `docs/guide-plan/coverage.md`: компактный индекс и тематические таблицы при необходимости. Для каждой записи нужны: источник/символы или группа файлов; ответственность; статья/раздел; статус; сверенная версия/ревизия; доказательство/проверка; оставшийся пробел; следующий ID патча. Статусы: `не проверено`, `частично`, `описано`, `историческое`, `служебное`. Последние два требуют основания, а не служат способом скрыть трудный модуль.

Разделять два учёта. **Инвентарь файлов** отвечает, у какого файла есть владелец/статья/основание исключения. **Смысловой охват** отвечает, описаны ли его ответственность, условия, переходы состояния, данные, ошибки и связи. У большого файла может быть несколько тем с разной готовностью. Простая ссылка или ненулевой reviewedVersion не закрывают все функции файла.

В охват включить рабочие модули, HTML/CSS и состояния UI; форматы и поля данных; тестовые семейства, инструменты, package/config/workflows и процесс документации. Автоинвентарь не включает все возможные расширения: отдельно проверить файлы конфигурации, фикстуры и ресурсы. Тесты можно группировать по проверяемому контракту; CSS — по ответственности интерфейса. Производные копии/архивы, неизменяемые снимки и личные файлы учитывать как исключения с причинами, без повторного построчного аудита.

Серия завершена, когда:

- у каждого действующего механизма, пользовательского сценария и формата есть доступное из приложения объяснение с проверенными источниками;
- все канонические файлы распределены по ответственностям, нет необъяснённых пропусков инвентаря, все смысловые пробелы закрыты либо явно перечислены как препятствия — при препятствиях «полное описание» не заявляется;
- покрыты цепочки между главами: пища → тело → ощущение → выбор/обучение → действие; геном → основатель/ребёнок → мутация; событие мира → история → архив → показатель → график;
- старые краткие главы проверены, разделены или связаны с подробными, поисковые запросы и выжимки ведут к нужному ответу; числа/контекст/ссылки актуальны;
- результаты проверок, ограничения реального просмотра и фактическая отправка записаны без преувеличения.

## Поддержка после серии

Каждый будущий патч механики проходит через её записи в реестре охвата: обновить статью, пример, привязки, выжимку и ссылки; проверить затронутые соседние главы. При изменении владельца обновить карту и паспорт. Новый файл получает тему и статус; удалённый/перенесённый — исправленные ссылки. Исторические результаты не переписывать под новое правило. Подстановка новых чисел не заменяет проверки нового смысла. Полная перечитка справочника при каждой косметической правке не нужна.
