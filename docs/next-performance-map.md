# Карта проекта: изменения, история и развитие

Статус: выполнен ручной блок карты по последующему поручению пользователя. [Карта](navigation/README.md), [охват и проверка](updates/v045-project-navigation.md). Генератор, автоматическая проверка устаревания, новые измерители, оптимизация и перенос рабочих модулей остаются предложениями.

## Уточнённая цель

Пользователь уточнил 21 октября 2026: навигация нужна для любых изменений текущих, прошлых и будущих частей проекта. Поиск узких мест — один из сценариев. Карта должна связывать задачу пользователя, действующую реализацию, основания прежних решений, проверки и будущий контракт при минимальном чтении контекста. Это уточнение цели, не поручение реализовать генератор или новую механику.

Ручная карта и связи «сейчас / история / будущее» созданы на существующих документах. Следующий возможный блок — отдельно согласовать генерацию/контроль актуальности и измерение удобства. Подробности открываются по теме; отдельные файлы на каждую функцию не создаются.

## Что обнаружено

- Есть START_HERE, architecture, правила контекста и ограничения размеров входных документов. Заново дублировать их содержание не нужно.
- architecture описывает владельцев, но не полные пути выполнения, частоты работы и доступные доказательства стоимости. Список импортов тоже не доказывает динамический путь вызовов.
- В performance-plan были смешаны исторические статусы с одинаковой пометкой «текущий». Теперь они вынесены в историю, действующий маршрут сверяется с benchmark-versions/fixtures.
- Повреждённые строки трёх служебных документов 0.45 восстановлены по прежним результатам. Проверка документов теперь замечает цепочки знаков вопроса и символ замены; ручная проверка смысла остаётся обязательной.

## Структура и дальнейшая автоматизация

Использовать существующий START_HERE как короткий вход, architecture как карту владельцев, work/current как единственную контрольную запись. Общий маршрут: «что изменить → тема → действующий код и проверки → история / будущий контракт по необходимости». Внутри него производительность получает маршрут «симптом → сценарий → функции → измеритель → проверки». Не создавать вторую энциклопедию механик.

Шесть направлений: подшаг/физика; основной и малый мозг/обучение/память; обмен и барьеры Workers; представление/Canvas; статистика/бутстрэп; импорт/архив/IndexedDB. Это области исследования, а не установленный список узких мест. Каждый путь нужно проверить по действующему коду.

Ручные карточки изменений уже указывают символы/границы/проверки. Расширенные карточки стоимости остаются предложением: последовательность ветвей, частота вызовов, влияющие размеры, копии/сообщения/ожидания, профиль и тест эквивалентности. Без актуального профиля не приписывать участку процент времени или обещанный выигрыш.

Предлагается генерировать механический индекс импортов/экспортов/ссылок на Workers и тестов. Он помогает искать, но не заменяет проверенную карту вызовов. Автоматически проверять наличие символов/ссылок и актуальность индекса по отпечатку исходников; не хранить вручную номера строк. Изменение затронутых модулей помечает связанные карточки требующими проверки.

Исторические снимки, source-files, архивы, релизы и временные логи исключать из обычного поиска и входного контекста, оставляя явный маршрут к ним. Канонические рабочие файлы сейчас в dist: не создавать вторую независимую копию и не переносить модули ради карты. Крупные профили читаются через короткую сводку с версией/отпечатком, нагрузкой, стадиями и ссылкой на первичные данные.

## Проверяемая польза и этапы

1. Служебные тексты восстановлены, история отделена, правила поддержки закреплены. Ручной индекс и карточки изменений выполнены без изменения модели.
2. После отдельного согласования добавить генерацию/проверку навигации; не инструментировать каждый внутренний вызов по умолчанию.
3. По выбранному симптому получить актуальный профиль; только затем согласовать оптимизацию и проверку эквивалентности.

Цель навигации: START_HERE и выбранный маршрут должны указывать нужный код, проверки, основания решения и будущий контракт без чтения всего проекта. Для оптимизации дополнительно нужен путь к измерению. Контролировать успешность поиска, объём прочитанных файлов/символов и ложные маршруты; экономию токенов и времени пока не измеряли. Историю и планы читать по необходимости, не включать их целиком в каждый вход.
