# Поддержание контекста агента

## Что читать

Обычный вход: `AGENTS.md` → `START_HERE.md` → контрольная запись → одна тема/нужные функции. Архив, полный журнал, все протоколы и все исходники заранее не читать. Получать компактные выдержки и результаты поиска; длинные логи сохранять в `.transfer`, пользователю/агенту выводить ошибки и итог. Сведения из старого чата сверять с дешёвой проверкой текущего файла.

Действующие правила работы — AGENTS; модель — соответствующий код и раздел справочника; намерение — принятый контракт. Архив хранит основания и отменённые варианты, не выдаёт новые поручения. `docs/current-model.md` и старые `next-*.md` могут быть историческими: проверять их собственную пометку/выпуск, не считать слово «next» разрешением кода.

## Один документ на обсуждение

Новый механизм/спорный объём обсуждать в одном тематическом контракте по [шаблону](../templates/contract.md). Уже существующий подходящий контракт использовать, не создавать копию для каждого вопроса. Идея получает одну короткую строку в [списке](../future-ideas.md). Направление стало принятым — краткая ссылка в [индексе решений](../decisions.md); числа/полный ответ туда не дублировать.

После блока из двух–трёх ответов менять пункты в том же контракте: принятое, открытые вопросы, заменённые варианты. Прежний отвергнутый вариант не оставлять равноправным действующим правилом. Существенное основание сохранить в короткой заметке/истории, остальное восстановимо из Git. Не дописывать одно и то же в START_HERE, decisions и future-ideas после каждого сообщения. Архивы/снимки и игровую версию при обсуждении не пересобирать.

## Статусы и разрешения

- `обсуждение`: предложения/неясности, код не разрешён;
- `согласован`: контракт готов, отдельного поручения реализации ещё нет;
- `разрешён`: пользователь поручил реализацию;
- `в работе`: разрешённый этап начат, следующий шаг конкретный;
- `выполнен`: результат/проверки и ограничения записаны;
- `заменён`: есть ссылка на новое решение, старое не действует.

Статус менять по фактам, не автоматически по заполнению шаблона. Автоматическая проверка не может установить истинность решения или дать разрешение за пользователя.

## Контрольная запись

[work/current.md](../work/current.md) содержит только активный законченный блок: статус, цель, режим, разрешённый объём, контракт, изменённые файлы, выполненные проверки и следующий шаг. Обновлять на границах этапов, перед прерыванием/новым чатом; не вести там посообщенческую историю. Если временные отчёты не входят в репозиторий, итог обязательно записать в протоколе с ограничениями проверки.

Несколько обсуждений могут иметь отдельные контракты, но текущая реализация одна: ссылки на отложенное в списке идей. Завершённая запись не поручает автоматически брать следующую идею. Для нового чата достаточно: «Продолжаем Big Evolution. Прочитай START_HERE и контрольную запись». Пользователю не нужно копировать весь разговор или повторять ответы, уже сохранённые в контракте.

## Завершение этапа

1. Проверить разрешённый результат, логику, стоимость и подходящие проверки; разделить измеренное и предполагаемое.
2. Обновить только затронутый раздел текущей механики/архитектуры и статус контракта. Закрытое убрать из активного списка, оставить ссылку на протокол.
3. Одним заключительным проходом записать протокол/итоги, при изменении модели создать снимок, обновить производные исходники/архив. Чистые документы не требуют версии игры, расчётного снимка или повторных биологических тестов.
4. Проверить ссылки и входной контекст: `python tools/verify-local.py --only docs`. Закрыть контрольную запись. Публикация — отдельное поручение.

## Ограничения объёма

[check-agent-context.py](../../tools/check-agent-context.py) проверяет размер входных файлов, обязательные поля записи и допустимый статус; ссылки/якоря — [check-project-docs.py](../../tools/check-project-docs.py). Лимиты считаются в символах, не токенах. Они не гарантируют понимание/ускорение, но останавливают накопление стенограммы во входе. История не ограничивается этими бюджетами и не загружается автоматически по ссылке.

При переносе сохранять содержание и действующие договорённости. Ссылки на старые разделы направлять в архив, ссылки без якоря — на текущий документ. Новые постоянные правила добавлять после реальной повторяющейся проблемы, не превращать AGENTS в справочник механик.
