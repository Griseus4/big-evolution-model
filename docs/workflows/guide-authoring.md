# Обязательный стандарт пособия «О проекте»

Действует для новых и изменяемых статей. Цель — самостоятельное понимание механики и поиск её реализации. Этот стандарт читают при работе с пособием после входа через AGENTS/START_HERE; всё пособие ради одной задачи не перечитывают. [Порядок поддержки документов](context.md), [объём и состояние пособия](../next-game-guide.md).

## Содержание статьи

1. Краткий ответ на понятный вопрос: что происходит и зачем это знать наблюдателю.
2. Разобранный пример с явно заданными исходными условиями.
3. Раскрываемые точные правила: состояние, доступные сведения, условия, порядок событий, единицы, расходы/результат, ограничения и крайние случаи.
4. Связанные темы: причины, последствия и отличие от похожих механизмов.
5. «Где это в коде»: файлы, символы, их назначение и соответствующие проверки.

Простой текст доступен без раскрытия технических деталей. Гипотеза, план, историческая версия и реализованное правило обозначаются раздельно. Субъективная оценка не подменяет выживание/потомство; личный опыт не подменяет наследуемый геном.

## Читаемость прежде перечисления

Главный критерий — человек быстро понимает правило и его связь с другими правилами. Объяснять связными предложениями, а не цепочкой названий и чисел через запятую. Для сопоставимых величин использовать небольшую таблицу с названиями и единицами; пункты — для параллельных вариантов, нумерацию — для последовательности. Не превращать каждый абзац в список и не повторять одну мысль в тексте, таблице и оговорке.

Не дописывать очевидные предостережения и общие слова об условности модели. Уточнение нужно, если оно меняет понимание механизма: например, отсутствие назначенных очков за поведение или мутации внутри одной родословной. Убирать дополнения, которые лишь уточняют и без того понятное слово.

Числа с единицами и точные названия элементов управления выделять умеренно: числовые значения — моноширинным начертанием, названия кнопок — как буквальные подписи, клавиши — kbd. Цвет текста не должен быть единственным носителем смысла. Ссылки внутри статьи выделять жёлтым и подчёркиванием; ссылки на статьи показывают выжимку при наведении/фокусе с принятой задержкой. Техническим ссылкам давать краткое описание назначения. Схему/график добавлять, когда они объясняют связь лучше текста, а не для украшения.

## Числа, формулы и контекст

- Источник правил — код. Не копировать константу или формулу в прозу вручную. Использовать именованную привязку к единственному источнику и общую функцию модели для расчётного примера. Кликабельная ссылка на исходник сама по себе не является такой привязкой.
- Для каждого подставляемого параметра определить источник/символ, единицы и область: постоянное правило, значение по умолчанию, принятые настройки текущего мира или конкретного варианта. Несколько вариантов не имеют одного неявного «текущего» значения. Черновик настроек не выдавать за состояние уже работающего мира.
- Произвольные числа допустимы как явно заданные входы учебного примера; вывод считать общей функцией, если она есть. Неподтверждённый результат не представлять выполненным расчётом.
- В guide-parameters.js реализованы именованные привязки времени усвоения и порогов родов: базовые значения, принятый основной мир или явно выбранный вариант загруженного/запущенного опыта. Обновление — при открытии статьи/пособия и выборе контекста, без работы на каждом подшаге. Другие настраиваемые числа добавлять в реестр; постоянные правила брать из экспортов модели. Полное автоматическое обнаружение устаревания прозы не реализовано. Объяснение причин и последствий требует содержательной сверки даже при актуальных числах.

## Паспорт и единственный источник

У статьи обязательны устойчивый ID, название, выжимка и термины поиска. У содержательно сверенной статьи — sources с символами, related, соответствующие проверки и reviewedVersion. Для статьи без содержательной сверки сохранять явный неполный статус. Не обновлять версию всех статей автоматически при выпуске.

Длинный текст хранить один раз. Выжимка и термины меняются при изменении смысла; указатели — при переносе реализации. Ссылки давать по устойчивым статьям/файлам/символам, без вручную поддерживаемых номеров строк. Старые перенесённые статьи не считать соответствующими стандарту только из-за наличия ID или источников.

## Работа над изменением

До редактирования найти затронутую статью через реестр и прочитать её источники/связанные темы. После изменения кода сверить условия, крайние случаи и числовые примеры; обновить только затронутые тексты, выжимки и указатели. Расхождение кода и принятого правила выяснить, не менять модель ради текста.

Перед завершением выполнить подходящие проверки и `python tools/verify-local.py --only docs`; указать реально выполненный охват. Нынешние проверки контролируют ссылки, символы, структуру и инвентарь, но не гарантируют истинность объяснения и не выявляют все устаревшие числа. Расширение именованных привязок на другие настройки и полное обнаружение устаревания зависимых правил остаются работой по контракту.

Новое решение сохранять в одном тематическом контракте до конца ответа; текущее состояние — в work/current. Для работы только над правилами документации версия игры не меняется. Готовые изменения публикуются по постоянному маршруту; обновление документов не разрешает описанный игровой код.
